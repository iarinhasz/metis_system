Metis em quatro módulos

Cada integrante é dono de um módulo e dos estágios do pipeline que ele contém. Cada etapa sai numa branch própria e entra na dev por PR. No fim de cada fase, a equipe testa a dev junta num ponto de integração e a promove para a main.

Onde estamos

O M0 está completo (0.1–0.7, na dev). Na F2, a 1.5 já divide o artigo de verdade, com chamadas ao Gemini conferidas contra o PDF; o GROBID foi descartado em 11/11 (pesado demais).

De onde vem

O roteiro tinha 3 trilhas (P, A, I). A trilha A reunia agents/, o M2 e o M3 e foi dividida em duas: Agentes, Perfil e Relatório, e Avaliação.

Como ler

F0 a F5 são fases sem data: uma fase termina quando o ponto de integração dela passa. Os números das etapas são os do plano completo, onde está o detalhe de cada uma.

Quem é dono de cada estágio

O artigo passa pelos estágios na ordem abaixo. A cor diz qual módulo constrói cada um.

  1. APISubmissãoPlataforma
  2. E1ExtraçãoPlataforma
  3. E2PerfilAgentes
  4. E3IntegridadeIntegridade
  5. gateRisco alto: revisão humanaPlataforma
  6. E4AvaliaçãoAvaliação
  7. E5ConsolidaçãoAgentes
  8. doneRelatório finalGET /report

Bases que todos usam

  • pipeline/ e attempts/, da Plataforma

    Todo estágio roda dentro do StageTask e muda o status só pelo RunManagement.

  • agents/, dos Agentes

    Toda chamada de LLM, do E1 ao E5, sai da AgentFactory; os testes usam a FakeAgentFactory.

  • ExtractedDocument, da Avaliação e depois da Plataforma

    O contrato que E2 a E5 leem. A Avaliação cria na 1.1, e a extração real (1.9) passa a produzi-lo.

  • scholarly/, da Integridade

    A única porta para Crossref, OpenAlex, Semantic Scholar, arXiv e Unpaywall. O E2 também usa, para a taxonomia.

Git e PR

Uma branch por etapa, criada a partir da dev e apagada depois do merge. Os PRs ficam pequenos, os conflitos diminuem e cada etapa vira um commit na dev.

Do início ao merge de uma etapa

  1. Atualize a dev local. git switch dev && git pull
  2. Crie a branch da etapa a partir dela: prefixo do módulo, nº da etapa e um nome curto. A coluna Branch das tabelas já traz o nome. git switch -c plataforma/0.5-gate-humano
  3. Implemente com os testes da etapa. Faça commits pequenos, em Conventional Commits e em inglês.
  4. Antes do PR, traga a dev e rode as checagens do CI. git fetch origin && git merge origin/dev uv run ruff check && uv run ruff format --check uv run mypy projects/correction && uv run pytest
  5. Envie a branch e abra o PR com base na dev. O título é o commit sugerido da etapa; o corpo segue o modelo ao lado. git push -u origin plataforma/0.5-gate-humano
  6. Com o CI verde e 1 aprovação, use Squash and merge e apague a branch. A próxima etapa começa no passo 1.

Revisão e merge

  • Todo PR vai para a dev. Ninguém faz push direto na dev nem na main.
  • O merge exige o CI verde (o check quality) e 1 aprovação de outro integrante, de preferência do módulo que consome a mudança (veja Dependências).
  • PR com o rótulo contrato precisa da aprovação de todos os módulos que consomem aquele contrato.
  • O squash transforma o PR num único commit na dev, com o título do PR. Assim cada etapa vira um commit, como pede a convenção.
  • Depois de um merge, quem tem branch aberta traz a dev (git merge origin/dev) antes de pedir revisão.
  • Na F3, os PRs da Avaliação têm prioridade de revisão: eles são o caminho crítico do I3.

Da dev para a main

  • No fim de cada fase, a equipe roda junta, na dev, a verificação manual do ponto de integração (tabela abaixo).
  • Passou: PR dev → main com merge commit (sem squash, para manter um commit por etapa) e a tag do ponto (i1 … i6) na main.
  • Não passou: a correção entra como PR na dev, e a verificação roda de novo.
